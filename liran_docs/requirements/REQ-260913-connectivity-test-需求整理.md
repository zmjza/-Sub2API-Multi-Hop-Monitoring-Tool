## 用户原始意图

用户希望参考 Wei-Shaw/sub2api 管理员账号管理中的“测试账号连接”功能，在当前“中转站悬浮窗”的“全部站点”总览卡片中新增“测试连通性”。用户确认采用主进程代理测试请求的方案，并暂时只实现普通文本请求；图片、音频、视频测试暂不实现。

## 已确认需求

### 0. 本轮追加范围

用户追加“使用记录统计优化”和“新旧渠道状态协议兼容”两项范围；两项与连通性测试同属本轮站点监控/使用数据增强，后续统一进入正式 PRD。

### 1. 入口位置

- 全部站点页面的每个站点卡片底部操作区，在“查看渠道状态”右侧新增“测试连通性”。
- 保留现有“查看倍率”“查看渠道状态”和充值比例功能。
- 新按钮必须遵守现有卡片底部固定槽位布局，不能因为新增按钮造成异常换行、溢出或卡片高度漂移。

### 2. 测试弹窗

- 视觉和交互参考 sub2api 的“测试账号连接”弹窗。
- 顶部显示当前站点信息和站点状态。
- 增加“选择 Key”下拉框。
- 选择 Key 后再选择测试模型。
- 只实现普通文本请求模式。
- 保留测试提示词输入；默认提示词采用 hi。
- 中部使用深色终端区域，实时显示连接、模型、响应和错误信息。
- 底部提供“关闭”和“开始测试”；请求进行中禁止重复提交。
- 支持失败后重试，关闭弹窗时取消正在进行的请求。

### 3. Key 选择规则

- 只展示当前站点的 active Key。
- 默认选中当前站点当前生效的 Key；没有手动选择时使用现有自动选择结果。
- Renderer 只传递 siteId、keyId、模型和提示词，不暴露完整 API Key。
- 主进程重新校验站点和 Key 状态，再读取真实 Key 执行测试。

### 4. 测试请求规则

- 测试请求必须实际使用用户选择的 Key，不能静默回退到默认 Key。
- 采用主进程代理方式，通过站点的普通文本模型接口发起一次真实请求。
- 测试结果至少包含：开始测试、选中 Key 的脱敏标识、模型、连接状态、响应文本、耗时或错误原因。
- 暂不实现图片、音频、视频、生图、语音、搜索和实时模式。

### 5. 安全边界

- 完整 API Key 只在主进程内处理，不进入 Renderer 状态、IPC 返回值、日志、截图或持久化缓存。
- UI 仅显示脱敏 Key 标签。
- 对 siteId、keyId、模型和提示词进行边界校验。
- 处理未登录、Key 不存在、Key 已停用、401、403、429、超时、模型不存在和上游连接失败。

### 6. 使用记录统计卡片

- 使用记录页面的“平均耗时”改为最近 100 次请求的平均耗时。
- 在“平均耗时”右侧新增“平均缓存率”卡片。
- 平均缓存率复用现有缓存率计算结果，取最近 100 次请求的缓存率求算术平均。
- 中转站模式与 OpenCodex 模式都使用相同的最近 100 次口径。
- 有效请求不足 100 次时，使用实际可用请求数计算，并显示实际样本数或等价提示；没有有效样本时显示占位符。
- 总请求数、总消费、平均耗时三张卡片适当缩窄，为新增平均缓存率腾出同一行宽度；桌面宽屏和窄窗口均不能溢出。
- 已确认统计口径：平均耗时取最近 100 条有有效 durationMs 的请求做算术平均；平均缓存率先按现有逻辑计算每条请求缓存率，再取最近 100 条有效缓存率做算术平均；不足 100 条按实际有效条数计算，无有效数据显示占位符；中转站模式和 OpenCodex 模式统一执行。

### 7. 新旧两种渠道状态协议适配

- 保留现有第一种渠道状态查询和展示，兼容旧版中转站。
- 新增 Sub2API channel-monitor-v2 矩阵查询适配，典型接口为：
  /api/v1/channel-monitor-v2/matrix?range=90m&group_by=platform_group&timezone=Asia/Shanghai
- 新版矩阵响应按 data.items[] 解析，使用 platform、group_id、group_name 作为渠道/分组维度，读取 metrics、health、buckets 和 coverage。
- 新版至少提取请求数、成功率/错误率、缓存率、TTFT 或 duration 平均值、健康等级、评分、时间桶和数据覆盖时间。
- 全部站点卡片、渠道状态页面、渠道状态弹窗、悬浮窗中涉及渠道状态的展示都支持新旧协议。
- 新旧协议归一化为当前 Renderer 使用的统一渠道状态模型，避免页面维护两套显示逻辑。
- 适配策略：每个站点先请求新版矩阵接口；只有明确确认新版不存在、未启用、返回 404/405、V2 模式未开启或响应不符合 V2 契约时，才回退旧版接口。新版出现临时网络错误、超时或 5xx 时先保留错误原因并按既有 stale/重试规则处理，不应未经判断直接把它当成旧版成功；旧版也不可用时才显示渠道状态不可用。
- 新版 coverage 的 data_through、computed_at、aggregation_lag_seconds 参与新鲜度判断，不能把尚未覆盖到的未来时间桶当成最新数据。
- 新版健康等级 healthy、warning、critical、unknown 与现有 normal、degraded、failed、unknown 建立稳定映射，并保留原始等级供详情展示。
- 新版矩阵按 platform_group 聚合，继续遵守现有 Key 分组与渠道严格匹配规则；不得仅按数组第一项或模糊包含关系关联渠道。
- 新版接口的 90 分钟窗口、5 分钟 bucket、bootstrap 未完成等情况需要在 UI 中正确表示数据覆盖范围和未知态。

### 追加确认：sub2api 当前仓库中的新版渠道监测

已再次核对 2026-09-13 拉取的 Wei-Shaw/sub2api 当前仓库源码，确认用户提供的 channel-monitor-v2/matrix 就是新版渠道状态监测接口，不是普通旧版渠道状态接口。

- 用户只读路由为 GET /api/v1/channel-monitor-v2/matrix，管理员路由为 GET /api/v1/admin/channel-monitor-v2/matrix。
- 两套路由都受 channel-monitor-v2 功能/模式开关保护；V2 未启用时不能把 404 或禁止响应误判为“渠道异常”。
- 请求支持 range、group_by、平台、分组、模型和时区等筛选；用户示例的 range=90m、group_by=platform_group、timezone=Asia/Shanghai 与上游实现一致。
- 上游用户版前端 ChannelStatusV2View.vue 通过 channelMonitorV2.ts 请求 /channel-monitor-v2/matrix，并按矩阵、趋势和详情统一展示。
- 上游矩阵模型为 data.group_by、data.coverage、data.items[]；每个 item 包含 platform、可选 group_id、group_name、可选 model、metrics、health、buckets。
- metrics 明确定义 request_count、success_rate、error_rate、cache_rate、ttft、duration 等字段；ttft.avg_ms 和 duration.avg_ms 都是上游提供的聚合值。
- health 定义 overall、error_rate、ttft、cache、score 和阈值；不能直接把 critical 当作旧版 failed，应保留原始健康等级并建立统一展示映射。
- coverage 包含 requested_start、requested_end、coverage_start、data_through、computed_at、aggregation_lag_seconds、bucket_seconds 和可选 bootstrap；这些字段用于判断数据是否完整、是否滞后、是否仍在回填。
- 上游用户版 V2 路由使用重型限流和 mode=v2 guard；适配器必须对未启用、不支持、权限不足做结构化降级，不能把所有请求错误归类为站点失败。

因此，本需求中的“新版本渠道状态”已确认来源和协议；后续实现应采用“逐站点 V2 探测 → 明确不支持时旧版回退 → 两者均不可用才报不可用”的顺序，并把两种响应归一化到现有渠道卡片、弹窗和悬浮窗模型。

已确认 UI 口径：不改动当前渠道状态页面、卡片、弹窗和悬浮窗的视觉结构与交互；新版 V2 只负责提供并归一化参数，最终继续按旧版现有方式显示渠道状态。V2 的健康等级映射、无流量语义、90m 固定窗口和错误回退均由适配层处理。

### 适配判定细则（待实现时验证）

- V2 探测请求必须复用站点现有认证、API 前缀、时区和取消/超时机制。
- 200 + 合法 V2 data.items/coverage 判定为 V2 可用，后续刷新优先继续使用 V2。
- 404/405、明确的功能未启用/模式不匹配错误、空响应或契约校验失败判定为 V2 不可用，并允许旧版回退。
- 401/403 判定为鉴权或权限问题，不能伪装成旧版成功；是否继续尝试旧版由站点能力和认证结果统一处理。
- 429/5xx/网络超时属于临时失败，保留错误与旧缓存，不能把一次临时失败永久记成“站点仅支持旧版”；可在下一刷新周期重新探测 V2。
- 站点能力应在内存缓存中记录为 v2、v1、unknown，但不能写入包含凭据的日志或持久化敏感数据。

### 8. 统一数据与状态边界

- V1 与 V2 先在主进程适配层解析，Renderer 只接收统一的渠道列表、详情、状态、时间线、指标和覆盖时间字段。
- V2 的 platform 与 group_id/group_name 只能映射到已有严格分组关系；无法唯一匹配时显示未知/待核验，不借用其他分组或数组第一项。
- V2 的 health.overall 映射为现有 UI 语义：healthy→normal，warning→degraded，critical→failed，unknown→unknown；无请求量优先为 unknown。
- V2 的 duration.avg_ms、ttft.avg_ms 仅用于渠道状态指标，不参与使用记录页面的平均耗时卡片。
- coverage.data_through 是数据有效上界；未来 bucket 和超过 data_through 的记录不得参与最新状态判断。
- coverage_complete=false 或 bootstrap.active=true 时保留可显示数据，但标记待核验/部分覆盖，不阻塞其他站点。

### 9. 刷新、缓存与降级

- 继续复用现有站点级单飞、并发上限、revision、防旧响应回写、stale-while-revalidate 和退避机制。
- 每个站点记录能力探测状态 unknown、v2、v1；临时失败不永久改变能力状态，下一周期重新探测 V2。
- V2 成功后同一站点后续刷新优先 V2；能力状态仅作内存优化，不能取代实际契约校验。
- V2 明确不支持后可在当前会话内优先 V1；应用重启或能力缓存失效后仍需重新确认。
- V1/V2 失败时保留旧数据并标 stale；没有旧数据时显示现有错误/未知空态。

### 10. 使用记录统计边界

- 最近 100 次按当前筛选结果的时间倒序取前 100 条，再分别过滤有效 durationMs 和有效缓存率样本。
- 数据加载层必须请求或读取足够记录，不能只对当前 20 条分页求平均。
- 过滤条件、站点切换、模式切换和刷新都会重新计算两张统计卡片。
- 统计卡片显示实际样本数，避免把少量样本伪装成 100 条稳定统计。

### 11. 连通性测试闭环

- 打开弹窗时加载该站点 active Key 和可用模型；加载失败时不能开始真实请求，并提供重试。
- 同一时间只允许一个活动测试；关闭、切换站点或组件卸载必须取消请求并阻止迟到事件回写。
- 普通文本请求由主进程按站点实际协议选择兼容端点；协议不支持时返回结构化错误。
- 成功、失败、取消、超时和重试都必须有明确终态；测试结果只保留在当前弹窗会话。

### 12. 验收与回归范围

- 统计覆盖中转站/OpenCodex 的 0、1、20、99、100、超过 100 条，以及缺失 duration/cache 和窄窗口布局。
- V2 覆盖合法响应、空 items、无请求、部分 coverage、bootstrap、未来 bucket、四种健康等级、404/405、401/403、429、5xx、超时和非法 JSON。
- V1 回归现有渠道列表、详情、时间线、缓存、手动关联、重试和悬浮窗。
- 兼容回归同一批站点混用 V1/V2、V2 成功后的持续刷新、明确不支持回退和临时失败重探测。
- 连通性回归 Key 切换、模型默认/手动选择、流式输出、取消、重试、错误脱敏和真实用量提示。
- 安全回归完整 API Key 不进入 Renderer、IPC 返回、日志、截图、测试夹具或持久化文件。

## 已由 Codex 统一确定的实现口径

- 普通文本测试由主进程按站点实际协议选择兼容端点；Renderer 不绑定单一协议。
- 模型列表优先复用站点已有模型/用量模型读取能力，必要时由适配器提供测试专用模型列表，但不新增重复请求链路。
- 测试请求计入真实用量，弹窗明确提示；不把测试结果持久化到站点卡片。
- 弹窗是否需要完全复刻参考图尺寸，还是沿用当前项目现有弹层规范。
- 平均耗时采用 duration、TTFT，还是按当前使用记录已有 durationMs 字段统一计算；当前需求已确认优先使用最近 100 条记录的现有可计算字段。
- 是否需要在部分站点尝试管理员 V2 路由；当前默认使用已登录用户可访问的 /api/v1/channel-monitor-v2/matrix，只有真实站点明确提供管理员会话时才考虑管理员路由。
