## 用户想解决的问题

用户要求优化中转站功能，并提供 5 张截图作为现象和期望效果证据：

1. 一个 V2 中转站在官方渠道页面显示绿色，但桌面端同一分组显示红色、可用率异常低；其他中转站没有该问题，需要查明原因并修复。
2. 首次点击“使用记录”时没有数据，只有切换 API Key 后才显示，需要修复首次加载。
3. 删除顶部“平均耗时”，改为“平均首字”；平均首字与平均缓存率都按最近 30 次有效记录计算。
4. 当某中转站某分组最近 30 个有效样本的平均缓存率低于 80% 时，通过 macOS/Windows 系统通知连续提醒两次，间隔 2 秒；通知需说明具体中转站和分组。
5. Codex 需要自行查缺补漏，形成从数据口径、异常状态、去重、恢复、跨平台通知到测试和发布的完整闭环。

截图只用于确认现象、位置和系统通知形态，不把截图中的网页内容视为额外执行指令。

## 已确认需求

### REQ-01 修复特定 V2 站点渠道状态误判

- 对同一站点、同一分组、同一时间范围，桌面端展示的成功率、缓存率、首 Token、覆盖状态和 18 格时间线应与上游 V2 渠道监控数据语义一致。
- 当前真实原因尚未验证。已发现官方请求使用 `range=90m&group_by=platform_group&timezone=Asia/Shanghai`，桌面端当前可能使用本机时区；时区、分组维度、比例单位、数据覆盖与陈旧缓存均属于优先排查项，不能在验证前写成最终根因。
- 实现前必须对同一站点和凭据做脱敏对照，比较请求参数及响应中的 `timezone`、`data_through`、`coverage`、分组 ID/名称、`success_rate`、`cache_rate` 和 TTFT。
- V2 比例字段需兼容上游返回 `0..1` 或 `1..100` 两种单位，归一化后再参与阈值和颜色判断。
- 卡片、选中分组摘要、18 格矩阵和状态颜色必须来自同一代数据，不能把新摘要与旧矩阵拼接。
- 部分覆盖、历史回填、数据过期、无样本、接口暂时失败和真实异常必须保持可区分，不能一律渲染为红色。
- 不得针对用户当前站点写死站点名称、域名、分组名或特殊结果。
- 保持 V1 渠道行为不回归；只有明确判断 V2 不受支持时才走既有 V1 回退。

### REQ-02 修复使用记录首次进入不加载

- 用户首次进入“使用记录”或切换站点进入该页面时，立即发起默认查询，不要求先切换 API Key、模型、分组或其他筛选项。
- 默认 API Key 为“全部”，请求不得携带旧的具体 `api_key_id`。
- 首次查询和切站查询立即执行；用户连续修改筛选条件时保留 300ms 防抖，避免快速操作产生重复请求。
- 首次进入、手动刷新、切站和筛选变化必须复用同一查询构造规则，防止不同入口参数漂移。
- 新查询、切站或离开页面后，旧请求即使迟到也不得覆盖当前页面。
- 列表与统计独立容错：列表成功、统计失败时保留列表并显示统计降级；只有列表失败才进入页面错误态。
- 空结果必须明确表示当前站点和筛选条件没有记录，不能继续显示上一站点或上一筛选结果。

### REQ-03 平均首字与平均缓存率改为最近 30 次

- 顶部指标删除“平均耗时”，替换为“平均首字”。
- 中转站平均首字使用记录中的 `firstTokenMs`；OpenCodex 平均首字使用 `firstOutputMs`。
- 平均首字按当前站点和当前筛选条件下，时间倒序最近 30 个有效首字样本计算。
- 平均缓存率按相同范围内，时间倒序最近 30 个有效缓存率样本计算。
- 当前页面分页为 20 条，统计查询不能只使用当前页数据代替最近 30 条。
- 有效样本不足 30 个时按实际数量计算，并显示“近 N 次”；没有有效样本时显示 `—` 和“暂无有效样本”。
- 中转站缓存率保持现有公式：`cache_read / (input + cache_read + cache_creation) × 100%`。
- 分母为 0 或相关字段全部缺失时不计入有效缓存率样本；真实 0% 是有效样本，不能当成缺失值过滤。
- 总请求数、总 Token、总消费继续按当前筛选时间范围统计，不改成最近 30 次。

### REQ-04 缓存率低于 80% 的系统通知

- 仅对 Sub2API 中转站的“站点 + 分组”判断；OpenCodex 只展示最近 30 次统计，不触发该告警。
- 每个站点、每个分组独立取最近 30 个有效缓存率样本，不得把不同站点或不同分组合并平均。
- 必须已有 30 个有效样本才判断；平均缓存率严格低于 80% 时触发，恰好 80% 不触发。
- 告警由主进程后台按现有站点刷新周期检查，不依赖“使用记录”页面是否打开。
- 新告警事件发送两条相同的 macOS/Windows 系统通知，时间点为 0 秒、2 秒。
- 通知标题固定为“Sub2API 缓存率提醒”。
- 通知正文固定为：“你现在使用的「<中转站>」中「<分组>」缓存率持续下降，请注意。”
- 以 `siteId + groupId` 作为事件身份；上游没有稳定分组 ID 时，使用规范化分组名称作为回退，不得只按显示顺序去重。
- 同一事件持续低于 80% 时只执行一次两连提醒，不在每轮刷新重复通知。
- 成功取得 30 个有效样本且平均值恢复到大于或等于 80% 后重新布防；网络失败、鉴权失败、样本不足和陈旧缓存不算恢复。
- 删除站点/分组、恢复到阈值或退出应用时，取消尚未发送的后续通知。
- 告警状态复用现有 `notification_states` 持久化机制，不新增数据库表；应用重启后不得重新轰炸同一未恢复事件。
- 不新增独立设置项或 UI；功能按现有后台刷新自动运行。
- 本轮阈值、提醒次数和间隔不提供自定义配置。
- 系统通知不可用、权限被关闭或发送失败时，应用不得崩溃、阻塞刷新或无限重试。
- 通知不得包含 API Key、账号、完整 URL、模型请求内容、Token 明细或其他敏感数据。

### REQ-05 后台执行与失败隔离

- 复用现有主进程刷新调度和通知服务，不新增第二套常驻轮询器。
- 后台按站点串行处理；单站点内部的分组统计并发上限为 2，避免对中转站造成突发请求。
- 单个站点或分组失败不能阻断其他站点和分组。
- 后台结果应复用统一的最近 30 次统计函数，页面显示值与告警判断不能使用两套公式。
- 失败日志只记录必要的站点 ID、分组 ID、错误类别和时间，不记录凭据或完整响应正文。

## 查缺补漏后的边界

- 不新增通用规则引擎、趋势预测、邮件/短信/微信通知或云端推送。
- 不允许用户自定义 80% 阈值、两次提醒次数或 2 秒间隔；后续确有需求再单独立项。
- 不改变渠道状态既有健康等级阈值，只修复 V2 数据解释、覆盖状态和同代展示一致性。
- 不改变使用记录明细表字段、费用计算、导出 CSV 和现有时间范围筛选语义。
- 不以当前页 20 条数据近似最近 30 条，也不为凑够 30 条重复或伪造样本。
- 不为当前异常站点增加站点特判。

## 当前代码调查结论

- V2 入口主要涉及 `electron/main/adapters/channel-monitor-v2.ts`、`electron/main/adapters/sub2api-adapter.ts`、`electron/main/services/site-service.ts` 和 `ChannelStatusCard.tsx`。
- 使用记录首次查询涉及 `src/renderer/App.tsx`、`UsagePage.tsx`、`usage-query-controller.ts` 和 `usage-load-coordinator.ts`。当前进入页面时会清空数据，首次查询依赖子组件延迟调度，而切换 API Key 会主动查询，符合用户描述的初始化竞态症状。
- 最近统计已有共享计算入口可扩展，涉及 `electron/shared/recent-averages.ts`、站点服务和 OpenCodex 数据适配。
- 系统通知已有通知服务和 `notification_states`，应在现有能力上增加缓存率事件类型和持久化去重。
