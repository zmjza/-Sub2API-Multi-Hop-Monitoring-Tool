## 1. 产品/功能概述

修复特定 V2 中转站在官方页面健康、桌面端却显示异常的问题；修复使用记录首次进入不加载；把“平均耗时”替换为最近 30 个有效样本的“平均首字”，并将平均缓存率统一为最近 30 个有效样本。某中转站某分组满 30 个有效缓存率样本且平均值严格低于 80% 时，应用在 macOS/Windows 于 0、2 秒发送两次系统通知，并在持续异常期间去重。

## 2. 背景与问题

- 用户的一个 V2 中转站在官方渠道页显示绿色，桌面端相同分组显示红色和异常低可用率；其他站点正常。
- 官方截图请求包含 `range=90m&group_by=platform_group&timezone=Asia/Shanghai`，桌面端当前可能使用本机时区。时区、分组维度、比例单位、覆盖状态和陈旧快照都是候选原因，最终根因尚未通过真实脱敏响应确认。
- 使用记录首次进入时会清空旧数据，首次查询依赖子页面延迟调度；切换 API Key 会主动查询，符合初始化竞态症状。
- 当前顶部“平均耗时”和“平均缓存率”使用的样本口径不符合用户需要，且页面分页 20 条，不能直接代表最近 30 次。
- 现有系统通知用于其他业务，尚未按站点+分组监控最近 30 次缓存率；本任务按用户确认自动运行，不新增独立设置。

## 3. 用户与使用场景

- 用户在渠道状态页对照上游官方页面，确认同一站点、同一分组和同一时间范围的健康状态。
- 用户首次打开使用记录或切换站点，希望无需操作 API Key 就立即看到数据或真实空态。
- 用户查看顶部统计卡片，希望快速了解最近 30 次请求的首字速度和缓存率。
- 用户不打开使用记录页面时，也希望后台持续监测各中转站分组的缓存率。
- 用户在 macOS 或 Windows 收到系统通知后，能从通知正文识别具体中转站和分组。
- 缓存率提醒无需新增单独 UI，按现有后台刷新自动运行。

## 4. 产品目标

1. V2 渠道状态与上游同一快照的分组、时间、比例、覆盖和颜色语义一致。
2. 使用记录首次进入和切站立即查询，默认查询全部 API Key，迟到响应不覆盖当前页面。
3. 平均首字和平均缓存率分别按时间倒序最近 30 个有效样本计算并显示真实样本数。
4. 某站点某分组满 30 个有效缓存率样本且平均值 <80% 时发送两次系统通知。
5. 持续异常只提醒一次；有效样本恢复到 >=80% 后重新布防。
6. 复用现有刷新、通知和持久化能力，保持 V1、OpenCodex、费用统计、CSV 和其他通知不回归。

## 5. 非目标与明确不做

- 不新增趋势斜率预测；“持续下降”通知文案只表示最近 30 次平均值低于 80%。
- 不新增邮件、短信、微信、云端推送或应用内通知中心。
- 不开放阈值、提醒次数和提醒间隔的自定义设置。
- 不新增数据库表、第二套后台轮询或通用规则引擎。
- 不改变现有渠道健康等级阈值，只修复 V2 数据适配和同代展示一致性。
- 不针对用户当前站点、域名或分组写死特判。
- 不改变使用记录明细字段、费用计算、CSV 导出和时间范围筛选语义。

## 6. 当前项目事实

- V2 渠道链路位于 `electron/main/adapters/channel-monitor-v2.ts`、`sub2api-adapter.ts`、`site-service.ts` 和 Renderer 渠道卡片。
- 使用记录初始化链路位于 `src/renderer/App.tsx`、`UsagePage.tsx`、`usage-query-controller.ts` 和 `usage-load-coordinator.ts`。
- 项目已有 `electron/shared/recent-averages.ts`，可承载共享最近样本计算。
- 项目已有主进程刷新调度、通知服务和 `notification_states` 持久化状态，不需要新建数据库表。
- 使用记录当前分页为 20 条，最近 30 次统计必须有独立数据来源或主进程统计结果。
- 中转站缓存率现有公式为 `cache_read / (input + cache_read + cache_creation) × 100%`。
- 项目目标平台为 macOS ARM64 和 Windows x64；Windows 无真机时只能记录交叉构建证据。

## 7. 用户流程

用户打开渠道状态 → 选择 V2 站点、时间范围和分组 → 应用按协议取得同一快照 → 页面用同一快照渲染摘要、卡片、18 格矩阵、覆盖状态和颜色 → 用户可与官方页面对照。

用户首次打开使用记录或切换站点 → 应用立即按“全部 API Key”查询列表和统计 → 页面显示加载、数据、空态或错误 → 用户继续修改筛选时使用 300ms 防抖 → 新查询使旧请求失效。

后台刷新站点 → 为每个 Sub2API 分组取得最近 30 个有效缓存率样本 → 样本满 30 且平均值 <80% → 立即发送第 1 条通知并在 2 秒发送第 2 条 → 持续异常不重复 → 有效样本恢复到 >=80% 后重新布防。

本功能不新增设置入口或独立 UI，系统通知沿用 Electron 与操作系统原生能力。

## 8. 功能需求

### REQ-01 V2 渠道状态一致性

触发条件：用户打开 V2 渠道状态、切换站点/分组/时间范围或后台刷新产生新快照。
前置条件：站点已配置有效凭据，上游支持 V2 渠道监控或能明确返回不支持。
用户操作：选择 90m、24h、7d、30d 时间范围，选择分组，刷新或等待自动刷新。
系统行为：按上游协议使用正确的时间范围、`group_by` 和时区；归一化 `success_rate`、`cache_rate` 等比例字段；摘要、卡片、18 格矩阵、颜色和更新时间绑定同一快照。
数据变化：只更新内存/既有缓存中的渠道快照和覆盖元数据，不修改站点凭据、分组或远端数据。
状态变化：loading、healthy、warning、abnormal、partial、bootstrap、no-sample、stale、error、unsupported 可相互转换。
正常结果：同一站点、分组和范围下，桌面端与官方接口的分组身份、成功率、缓存率、TTFT、覆盖和数据截止时间语义一致。
异常处理：非法或缺失比例进入无样本/异常数据状态；部分覆盖、回填、过期缓存和请求失败分别显示；明确不支持 V2 才回退 V1。
禁止行为：禁止写死站点、域名或分组；禁止把所有非完整数据渲染为红色；禁止混用不同代摘要和矩阵；禁止破坏 V1。
对应 AC：AC-01、AC-02、AC-03

### REQ-02 使用记录首次加载与请求隔离

触发条件：首次进入使用记录、切换站点、手动刷新或筛选变化。
前置条件：当前站点存在且使用记录页面可调用现有查询接口。
用户操作：进入页面，切换站点/API Key/模型/分组/时间范围，刷新或离开页面。
系统行为：首次进入和切站立即查询；连续筛选变化使用 300ms 防抖；默认“全部 API Key”不携带 `api_key_id`；所有入口复用同一查询构造；新查询、切站和离页使旧请求失效。
数据变化：只更新当前页面列表、统计、分页和加载/错误状态，不修改站点、Key 或远端记录。
状态变化：idle、loading、success、empty、partial-stats、error、refreshing；旧请求进入 discarded。
正常结果：用户无需切换 API Key 即看到当前站点记录或真实空态，列表与统计属于同一筛选范围。
异常处理：列表成功、统计失败时保留列表并降级统计卡片；列表失败显示可重试错误；迟到响应静默丢弃。
禁止行为：禁止沿用旧具体 Key；禁止让统计失败清空成功列表；禁止显示上一站点或上一筛选结果。
对应 AC：AC-04、AC-05、AC-06

### REQ-03 最近 30 次平均首字与平均缓存率

触发条件：使用记录查询成功、筛选变化、切站或手动刷新。
前置条件：已取得按时间排序所需的使用记录或等价统计结果。
用户操作：查看 Sub2API 或 OpenCodex 使用记录顶部指标卡。
系统行为：删除“平均耗时”，显示“平均首字”；Sub2API 使用 `firstTokenMs`，OpenCodex 使用 `firstOutputMs`；平均首字和平均缓存率分别取时间倒序最多 30 个有效样本。
数据变化：只产生派生统计值和各自样本数；总请求数、总 Token、总消费仍按完整筛选范围计算。
状态变化：loading、value-with-count、no-valid-sample、stats-error。
正常结果：卡片显示平均值和“近 N 次”；不足 30 个按实际样本数，无有效样本显示 `—` 和“暂无有效样本”。
异常处理：非有限首字值不计入；缓存率分母为 0 或字段全缺失不计入；真实 0ms 和 0% 均计入；统计失败不影响明细列表。
禁止行为：禁止用当前页 20 条代替最近 30 条；禁止重复或伪造样本；禁止把总请求/Token/消费改为最近 30 次。
对应 AC：AC-07、AC-08、AC-09

### REQ-04 缓存率低于 80% 的后台系统通知

触发条件：后台刷新取得某 Sub2API 站点某分组的最新使用记录统计。
前置条件：分组存在稳定身份，已取得 30 个有效缓存率样本，数据不是过期缓存。
用户操作：无需打开页面；等待后台检查并查看系统通知。
系统行为：各站点、各分组独立计算最近 30 次平均缓存率；严格 <80% 创建一次事件，并在 0、2 秒发送两条相同系统通知；标题为“Sub2API 缓存率提醒”，正文为“你现在使用的「<中转站>」中「<分组>」缓存率持续下降，请注意。”
数据变化：以 `siteId + groupId` 持久化事件状态；无稳定 groupId 时使用规范化分组名；复用 `notification_states`，不新增表。
状态变化：armed → notifying → alerted；有效样本满 30 且平均值 >=80% 时回到 armed；失败、样本不足和陈旧数据保持原状态。
正常结果：持续低于阈值只完成一次两连提醒；恢复后再次跌破可产生新事件；应用重启不重复轰炸同一未恢复事件。
异常处理：网络/鉴权失败、样本不足不告警也不恢复；通知权限关闭或发送失败不崩溃、不阻塞刷新、不无限重试；单组失败不影响其他组。
禁止行为：禁止监控 OpenCodex；禁止混合站点或分组平均；禁止在通知中包含 API Key、账号、完整 URL、请求内容或 Token 明细。
对应 AC：AC-10、AC-11、AC-12、AC-13

### REQ-05 并发和生命周期清理

触发条件：应用启动、站点/分组删除、恢复达标或应用退出。
前置条件：刷新调度和通知服务可用。
用户操作：删除站点/分组，或退出应用。
系统行为：功能自动运行；站点间串行，单站点内分组并发上限 2；删除、恢复和退出时取消剩余通知。
数据变化：只更新对应通知状态，不修改余额提醒或其他通知状态。
状态变化：待发送定时器在 deleted、recovered、app-exit 时进入 cancelled。
正常结果：事件去重和定时器生命周期一致，其他通知与站点刷新保持可用。
异常处理：单站点/分组失败隔离；应用退出清理全部待发送定时器。
禁止行为：禁止新增独立设置 UI、第二套轮询或清空无关通知状态。
对应 AC：AC-14、AC-15、AC-16

## 9. 数据、状态与业务规则

- 最近 30 次先按时间倒序，再按指标独立筛选有效样本；两个指标的 N 可以不同。
- Sub2API 缓存率公式固定为 `cache_read / (input + cache_read + cache_creation) × 100%`；缓存创建字段不得重复累计。
- V2 比例字段统一归一化为 0..100；`0.984` 与 `98.4` 均应显示 98.4%。
- 告警阈值是严格小于 80%；79.99% 触发，80.00% 不触发。
- 告警必须恰有 30 个有效样本后才判断；29 个或更少不判断。
- OpenCodex 展示最近 30 次统计，但不触发缓存率系统告警。
- 通知事件身份优先使用 `siteId + groupId`，没有稳定 ID 时使用规范化分组名。
- 页面统计和后台告警复用同一有效样本与缓存率计算规则。

## 10. 页面与 UI 需求

- 使用记录顶部原“平均耗时”卡片改为“平均首字”，保留现有卡片布局、图标层级和响应式规则。
- 平均首字和平均缓存率卡片副文案显示“近 N 次”；无样本显示“暂无有效样本”。
- 不新增缓存率提醒设置控件或独立 UI，页面继续沿用当前视觉方案。
- 渠道状态继续使用现有卡片、摘要和 18 格布局，只修正数据与状态语义，不创建新页面或新视觉体系。
- loading、empty、partial、stale、error 和 no-valid-sample 必须有可区分文案/状态，不用红色代替所有异常数据条件。
- macOS 和 Windows 通知使用系统原生样式，应用不仿造截图中的系统通知 UI。

## 11. 异常、边界与安全规则

- 真实 V2 根因验证只能记录脱敏请求参数、字段差异和结论，不记录完整凭据或完整响应正文。
- 比例值缺失、非有限或越界时不能直接进入健康阈值判断。
- 网络失败、鉴权失败、样本不足、过期数据都不算“恢复”。
- 切站、切分组、切筛选和离页后的迟到请求不得覆盖当前状态。
- 两连通知必须可取消；恢复、删除和退出后不得继续弹出剩余通知。
- Renderer 不新增 Node、数据库或任意通知权限；通知仍由主进程受控服务发送。
- 日志只记录必要的站点 ID、分组 ID、错误类别和时间，不记录 Key、账号、URL 或响应正文。

## 12. 兼容性与限制

- 保持 V1 渠道状态协议和现有回退行为，不将 V2 特性强加给 V1。
- 支持项目现有 macOS ARM64 和 Windows x64 构建目标。
- macOS 必须完成真实系统通知和可见窗口验收。
- 没有 Windows 真机时只记录 NSIS 交叉构建、结构和资产验证，不声称 Windows 通知真机通过。
- 系统通知权限由操作系统管理；权限关闭时应用只能安全降级，不能绕过系统设置。
- V2 上游字段和单位可能因站点版本不同而变化，适配必须基于协议证据和夹具覆盖，不做站点硬编码。

## 14. 验收标准

### AC-01 V2 真实站点对照

对应需求：REQ-01
验收步骤：使用同一站点、凭据、分组和时间范围，对照官方请求与桌面端脱敏请求/响应字段。
预期结果：timezone、data_through、coverage、分组身份、success_rate、cache_rate 和 TTFT 语义一致，页面不再错误显示红色。
失败条件：仍存在未解释差异、使用站点特判、不同代数据混合或无证据声称根因已修复。

### AC-02 V2 比例、覆盖与 V1 回归

对应需求：REQ-01
验收步骤：分别输入 0.984/98.4、缺失、越界、部分覆盖、回填、无样本、过期、失败和 V1 夹具。
预期结果：两种比例均显示 98.4%；非完整数据进入对应状态；V1 行为不变。
失败条件：比例放大/缩小错误、所有非完整数据均为红色、V1 被 V2 逻辑影响。

### AC-03 V2 快照与迟到响应

对应需求：REQ-01
验收步骤：快速切站、切分组、切范围并制造旧请求迟到。
预期结果：摘要、卡片、18 格和颜色始终属于当前选择的同一快照。
失败条件：旧响应覆盖当前选择或页面混合两代数据。

### AC-04 使用记录首次进入

对应需求：REQ-02
验收步骤：从其他页面首次进入使用记录，不操作筛选器。
预期结果：立即发起全部 API Key 查询并显示数据或真实空态。
失败条件：必须切换 API Key 才加载、请求携带旧 key 或页面保持空白。

### AC-05 使用记录切站与快速筛选

对应需求：REQ-02
验收步骤：切站、具体 Key→全部、快速切换模型/分组/时间并制造旧请求迟到。
预期结果：首次/切站立即查询，连续筛选 300ms 防抖，旧响应丢弃，全部查询无 `api_key_id`。
失败条件：旧结果覆盖、新旧参数漂移、全部仍使用具体 Key。

### AC-06 列表与统计独立容错

对应需求：REQ-02
验收步骤：分别模拟列表成功统计失败、列表失败、空结果和重试。
预期结果：统计失败保留列表；列表失败显示可重试错误；空结果不显示旧数据。
失败条件：统计失败清空列表或失败后残留上一范围数据。

### AC-07 最近 30 次首字

对应需求：REQ-03
验收步骤：准备 50 条记录，其中首字有效、缺失、0ms 和非有限值混合。
预期结果：按时间倒序取最近 30 个有效样本；Sub2API/OpenCodex 使用各自字段；显示真实 N。
失败条件：使用平均耗时、取当前页 20 条、过滤真实 0ms 或纳入无效值。

### AC-08 最近 30 次缓存率

对应需求：REQ-03
验收步骤：准备有效 0%、零分母、字段缺失和超过 30 条的记录。
预期结果：真实 0% 计入；零分母/全缺失排除；按最近 30 个有效样本平均。
失败条件：0% 被过滤、零分母被当 0%、重复累计 cache_creation 或取错范围。

### AC-09 统计空态与范围回归

对应需求：REQ-03
验收步骤：分别构造 0、18、30 个有效样本并检查总请求、Token 和消费。
预期结果：0 个显示 `—/暂无有效样本`，18 个显示近 18 次，30 个显示近 30 次；其他总计仍按完整筛选范围。
失败条件：样本数文案虚报或全量统计被改成最近 30 次。

### AC-10 告警阈值与两连时间

对应需求：REQ-04
验收步骤：使用可控时钟构造 29 个、30 个 79.99%、30 个 80.00% 样本。
预期结果：仅 30 个且平均 <80% 的事件在 0、2 秒各发送一次。
失败条件：样本不足触发、80% 触发、次数/间隔错误或重复创建事件。

### AC-11 去重、恢复与重启

对应需求：REQ-04
验收步骤：持续低于 80%、应用重启、恢复到 >=80%、再次跌破。
预期结果：持续异常和重启不重复；恢复后重新布防；再次跌破产生新两连提醒。
失败条件：通知轰炸、失败/样本不足被当恢复或恢复后不能再告警。

### AC-12 分组隔离与失败隔离

对应需求：REQ-04
验收步骤：准备多个站点/分组，制造单组请求失败并记录并发数。
预期结果：各组独立平均和状态；单组失败不影响其他组；单站点内并发 <=2。
失败条件：跨组混算、一个失败中断全局或并发超过上限。

### AC-13 通知内容与平台降级

对应需求：REQ-04
验收步骤：检查 macOS 系统通知、Windows 可用证据或结构测试、权限关闭和发送失败。
预期结果：标题/正文符合约定且无敏感信息；不可用时应用继续运行且不无限重试。
失败条件：泄漏凭据、平台错误导致崩溃或把 Windows 交叉构建冒充真机通过。

### AC-14 无新增独立 UI

对应需求：REQ-05
验收步骤：检查设置页、共享设置契约和后台刷新入口。
预期结果：不新增缓存率提醒控件或设置键，功能自动运行且不改变余额提醒。
失败条件：出现多余设置 UI、复用余额开关或改变其他通知行为。

### AC-15 定时器取消

对应需求：REQ-05
验收步骤：第 1 条通知后分别恢复、删除站点/分组和退出应用。
预期结果：第 2 条通知被取消。
失败条件：取消后仍弹第 2 条或重启补发旧通知。

### AC-16 综合回归与发布

对应需求：REQ-01、REQ-02、REQ-03、REQ-04、REQ-05
验收步骤：执行格式、lint、typecheck、单元/集成/E2E、生产构建、macOS 真机、Windows x64 构建、完整 diff 和统一发布流程。
预期结果：3.5.0、CHANGELOG、同提交双平台资产、两个远端和 GitHub Release 全部可验证；pitfalls 已回写。
失败条件：任一必需检查失败、旧资产复用、版本/说明不一致、未验证就声称发布或 Windows 真机通过。
