## 2026-07-12 首次原话

> 我想做一个sub2api 中转站额度查询和使用记录查询。
> 因为我有很多个中转站。我想做一个悬浮窗形式可以实时查看剩余额度，当前中转站apikey倍率，使用记录，渠道状态。同时想看其他的中转站，点击切换就能了。你帮我想想这个方案怎么实现，我们应该需要多轮对话吧需求整理好

## 2026-07-12 确认结果与变更记录

- 中转站均为 sub2api 二开站，使用普通用户账号；登录无验证码。
- 放弃以 Playwright 多开浏览器作为查询主链路，改为直接调用 HTTP API。
- 同时兼容 macOS 与 Windows，当前真机验收由 Codex 在 macOS 完成；Windows 只做 CI 构建、启动和核心自动化验证。
- 站点规模按 6–20 个设计，使用动态并发、随机刷新、错峰和退避。
- 首次启动必须测试登录成功后才能保存站点；支持常用账号模板和批量录入。
- 悬浮窗默认右上角，可切换左上角；左右切换站点，点击打开主面板。
- 默认 API Key 支持自动与手动模式；自动模式选择今天请求次数最多的 Key，手动模式永久保存并优先。
- 今日统计显示总 Token、输入、输出、缓存、实际消费和标准费用；金额按美元原值显示。
- 低余额通知阈值为 0.50 美元，通知总开关默认关闭。
- 动态标题按当前站余额切换两句用户确认文案，并有查询中兜底文案。
- 使用记录、渠道状态和主面板后续采用 `@product-design + Stitch / Stitch MCP` 高保真 UI 壳路线。
- 源代码发布到 Gitee：`https://gitee.com/zarq/Sub2API-Multi-Hub-Monitoring-Tool.git`。
- 用户确认需求总结无误，并选择 Codex 负责 macOS 真机测试及 Stitch Design QA。
- 用户曾确认文本视觉方案支持浅色、深色与跟随系统、默认浅色；该主题范围已被后续确认取代。液态玻璃适用边界不变。
- 用户确认密集表格、表单、渠道时间线和危险操作区使用高不透明表面，并要求支持减少透明效果与高对比度降级。
- 用户确认本项目不需要额外视觉图片。以上为设计确认，不代表 UI 壳、Stitch 产物或 Design QA 已完成。
- 2026-07-12 后续变更：取消深色模式、跟随系统模式和主题切换，产品只提供固定浅色模式；减少透明效果与高对比度作为浅色模式下的无障碍降级继续保留。此项为需求确认，不代表代码或 Stitch 产物已经同步完成。
- 2026-07-12 用户提供 Stitch 项目 `Sub2API 桌面监控台`（Project ID：`10340103531009759971`）及 5 个最新优化业务 Screen 和 1 个 Design System 资产，要求以最新 HTML 原型更新文档体系、模块、微观任务和 UI 壳清单。该确认只代表原型输入已提供，不代表真实 UI 壳、业务接线、Design QA 或真机验收已完成。
- 最新原型中“常用账号”归入“站点管理与设置”的内部 Tab，不新增独立主导航 Screen；常用账号业务需求本身继续保留。
- 2026-07-13 后续变更：用户明确取消“常用账号”整项功能，不作为页面、主导航、内部 Tab、数据模型或开发任务保留；站点自身的账号密码录入和安全凭据存储仍保留。此变更取代上一条“作为内部 Tab 保留”的旧确认。
- 2026-07-13 视觉收口变更：Stitch 路线不执行 Product Design Design QA，不使用 P0/P1/P2 或 90% 相似度作为门禁；改为以 Stitch HTML 为第一事实来源的实例级规格复修与接收检查。
- 2026-07-13 尺寸确认：Renderer 内部设计画布为 `1440 x 1024`；Electron 主窗口初始宽度为主屏可用工作区 `60%`、高度为 `90%`，可缩放并自动居中；主 UI 基于设计画布等比缩放，左侧菜单固定，悬浮窗保持独立固定尺寸。

## 2026-07-14 深度优化确认

- 用户要求主窗口和悬浮窗去除原生黑色标题栏；主窗口最小化切换为悬浮窗，主窗口关闭按钮真正退出，悬浮窗扩大按钮恢复并聚焦主窗口。
- 用户确认 `1440 x 1024` 只作为 Stitch 视觉参考，Renderer 应铺满当前窗口；主窗口仍默认占主显示器可用宽度 `60%`、高度 `90%`，可从边缘和四角缩放，左侧菜单固定。
- 用户取消全部站点中的悬浮窗预览和固定“正在获取余额”文案；加载、成功、过期和失败必须来自真实请求状态。
- 用户要求 Token 在界面按 K/M 紧凑显示；使用记录每页最多 20 条，时间本地化，增加思考等级列，删除地区列，并为站点、模型、分组和 Key 提供真实下拉选择。
- 用户要求倍率从真实 Key/分组数据解析；渠道超过 6 个时列表独立滚动，状态徽标移到 PING 附近，站点或渠道切换时不得用旧数据冒充新结果。
- 用户要求单站和批量验证显示真实阶段、进度和最终成功/失败原因；通知与通用设置必须具备可持久化的实际功能。
- 用户要求悬浮窗支持四角停靠、默认右上并持久化，采用非置顶桌面常驻而非始终置顶，并显示真实状态与更新时间。

## 2026-07-14 悬浮窗桌面层最终确认

- 用户确认悬浮窗切换到浏览器或其他软件后不能自动最小化、隐藏或关闭，除非用户点击悬浮窗扩大按钮打开主界面。
- 用户确认“只能在桌面”不等于置顶：浏览器和其他前台应用必须能够覆盖悬浮窗，悬浮窗不得遮挡正常前台工作。
- macOS 已开启台前调度，需要在不同 Space/台前调度组之间保持悬浮窗存在，但不得覆盖全屏应用；Windows 同样使用普通窗口层，不做置顶窗口。
- 应用版本继续保持 1.0 系列，工程和安装包采用 SemVer `1.0.0`。
- 本节为最新用户确认，覆盖此前可能把“桌面常驻”理解为置顶或切换应用时隐藏的表述。
- 2026-07-15 复测发现 macOS 台前调度仍会影响悬浮窗显示；用户再次确认桌面常驻显示路径不得激活应用或调用焦点切换，Windows 也必须采用同一非激活显示语义。
- 用户要求本轮由一个主智能体统筹，是否启用子代理由主智能体判断；任一时刻最多四个子代理，完成后及时回收。Codex 负责 macOS 真机与页面样式检查，Windows 只做交叉构建和自动化证据。
- 用户要求重新生成 macOS ARM64 DMG 与 Windows x64 NSIS 安装包并放在项目根目录。以上均为本轮需求确认，不等于已经实现、验证或打包完成。
