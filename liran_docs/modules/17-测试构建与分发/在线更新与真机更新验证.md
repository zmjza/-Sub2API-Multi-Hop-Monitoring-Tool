# 在线更新与真机更新验证

## 状态

核心代码已实现，按用户确认跳过独立 UI 壳路线，并直接在现有 Renderer 页面局部接入。1.4.8 GitHub Release 已发布并完成双平台资产与 manifest 校验；macOS 打包应用更新反馈和版本徽标已完成真实验收，Windows 自动安装仍未进行真机验证。1.4.8 增加检查中/最新/失败消息和新版本询问弹框。

## 目标与范围

为现有 Electron 应用增加稳定版在线更新能力：启动时、设置页和主界面右上角版本徽标均可触发检查；发现新版本时显示版本号、更新内容、下载进度和错误状态；支持立即更新、跳过此版本和稍后提醒。Windows 尝试下载、安装并自动重启；macOS 在当前免费 ad-hoc 签名边界下检查、下载并打开 DMG，必要时由用户手动替换 App。

本需求不包含 beta 渠道、付费托管、付费签名、公证、云同步、遥测、远程代码执行或站点业务接口改造。

## GitHub 发布与 Gitee 镜像

- GitHub Release 作为唯一安装包发布渠道；Gitee 只配置 GitHub Pull 镜像，用于国内源码拉取，不同步 Release 附件。本项目使用自定义 `update-manifest.json`，不依赖 electron-builder 的 `latest.yml`/`latest-mac.yml`。
- 发布元数据必须通过 HTTPS 获取，版本、平台、架构、下载 URL、SHA-256、发布日期和更新说明必须相互一致。
- 更新说明来源为 `CHANGELOG.md` 和 GitHub Release 文案；不能从远程内容执行代码或读取站点数据。
- 稳定版只保留一个更新通道，不引入 beta 标记。
- 每个 GitHub Release 固定同时提供两个平台：`mac-arm64.dmg` 为 macOS ARM64，`win-x64.exe` 为 Windows x64；两个平台的 `.blockmap` 与 `update-manifest.json` 必须一起上传，并在 Release 说明中解释文件对应平台。GitHub Release 支持大于 100 MB 的单文件，不做分片。
- 1.4.6 及更早旧客户端如果内置 Gitee 更新地址，不会因为远程 GitHub Release 出现而自动切换；这类客户端必须先安装包含 GitHub 更新服务的版本。

### 固定发布命令

后续版本发布统一执行：

```bash
npm run release:publish -- --notes "本次更新说明"
```

命令会校验 SemVer 和 `CHANGELOG.md`，要求工作区干净，构建并校验双平台安装包、两个 blockmap 与 manifest，创建并推送版本标签，从 macOS Keychain 的 `sub2api-github-release-token` 读取 GitHub API 令牌，上传并复核远端 Release。真机更新测试 patch 使用 `--test-only`，命令会自动追加“真机更新测试专用、无业务功能变化”。发布前可用 `--dry-run` 做无副作用检查。

## 真机更新测试批次

允许发布递增 patch 版本，例如 `1.4.6`、`1.4.7`、`1.4.8`，只改变版本、构建产物和发布说明，不改变业务代码。每个测试版本的说明必须包含：`真机更新测试专用`、`本版本不包含业务功能变化`、`仅用于验证更新检查、下载、安装、重启和数据保留`。测试批次不得冒充功能发布；历史测试包需在 GitHub Release 或外部归档保留，不能用旧文件冒充当前版本。

## 数据、安全与回退

- 更新前后保留 SQLite、站点配置、应用偏好、safeStorage/Keychain/DPAPI 数据；不新增敏感数据上传路径。
- 跳过版本、稍后提醒时间和最近检查结果只能保存为非敏感设置。
- 下载校验、签名验证、版本比较和安装失败回退必须由主进程控制；Renderer 不直接下载或安装任意 URL。
- 关闭、退出、刷新、CSV 导出或站点写入进行中时，自动重启策略必须有明确行为；未知时标记待确认，不丢数据。
- 更新失败、网络中断、元数据损坏、版本回退、平台不匹配和磁盘不足均必须保留当前版本可启动。

## 现有页面接入范围

直接复用现有页面接入：右上角版本徽标可点击态、站点管理/设置页更新区、无更新/有更新/下载中/已下载/跳过/稍后/失败/平台降级/重启提示等状态；主进程通过 preload 预留 `check`、`download`、`install`、`openDmg`、`skip`、`remindLater`、进度事件和错误事件。本轮明确不创建空壳、不生成 Stitch 或 Product Design 提示词，不新增 `ui-shells` 文件。内部测试通过后，在同一条 `/goal` 继续执行可用平台的真实验收、问题修复和证据回写。
